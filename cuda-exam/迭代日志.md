# CUDA 优化迭代日志（Water2GPU · GPU Laplace 求解器）

> 本文档记录 Water2GPU 项目中 GPU 计算核（当前聚焦 hydro 水面 Laplace 求解器）**每一次优化迭代的
> 决策与结论**（文字描述，非代码）。每个 CUDA 优化 = 一个版本迭代。之后的迭代信息持续追加于此。
>
> **阅读方式**：每条迭代含「背景 / 做法 / 结果 / 结论」。负结果（如 cuDSS）同样是有价值的迭代，保留为证据。
>
> **贯穿铁律**：数值保真第一——GPU 解与 CPU 金标准（faer 直接解 / Python `spsolve`）逐像素对拍 < 1e-6；
> GIS 底层统一经 eci-gdal；真实地形三方对比（Python / Rust / GPU）强制记录（合成基准常过于乐观）。

## 环境基线

- **硬件**：RTX 5070 12GB，Blackwell **sm_120**，**FP64 = 1/64 FP32**（消费卡，双精度受限）。
- **软件**：Ubuntu 24.04（WSL），CUDA Toolkit 13.3，驱动 610.47，Rust 1.96.1。
- **CPU 金标准**：faer 0.24 稀疏 Cholesky（AMD 重排序 + supernodal）；Python 基线 scipy `spsolve`。
- **规范**：每个计算核 = `cuda/xxx.cu`（主机 launcher + 设备核 + `CUDA_CHECK` 严格校验 + `cudaEvent` 分段计时）
  + `cuda/xxx.cuh`（接口）；`build.rs` 用 nvcc 编静态库，Rust FFI 调用。对标 NVIDIA cuda-samples。

## V1 —— GPU 加速骨架（commit `5844552`）

- **背景**：项目第三代（MyProject Python → Water2Rust 纯 Rust CPU → water-cuda GPU 加速）。需在 rust/shadcn
  CPU 版之上叠加 CUDA 计算核层，跑通最小端到端证据。
- **做法**：搭建 water-gpu crate（`.cu`/`.cuh` + build.rs nvcc + FFI）；`common.cuh` 提供 `CUDA_CHECK` /
  核后检查 / 显存充足性检查 / `CudaTimer` 事件计时 / `WaterKernelTiming`（H2D/kernel/D2H，与 Rust `#[repr(C)]` 对齐）；
  最小 `vector_add` 核自检。eci-gdal 作 submodule。
- **结果**：向量加与 CPU bit-exact 一致，端到端链路（H2D→kernel→D2H + 分段计时）打通。
- **结论**：骨架成立，具备逐模块 GPU 化的基础设施与计时/校验规范。

## V2 —— cuDSS 直接稀疏 Cholesky（证伪 · 保留为证据）

- **背景**：hydro 瓶颈是水面 Laplace 求解。首选尝试用 NVIDIA cuDSS 在 GPU 上做直接稀疏 Cholesky 替换 faer。
- **做法**：接入 cuDSS 0.8（pip wheel，`cudss` 特性门控），装配 CSR 后 GPU 直接解。
- **结果**：数值 parity OK（~1e-14），但**性能比 faer 慢 2–25×**。根因（第一性原理）：稀疏 Cholesky 的
  符号分析（analysis）阶段不规则、走主机串行，单次求解无法摊薄；`HOST_NTHREADS` 无效（analysis 不并行）；
  hydro 每多边形单次解，无多 RHS/refactor 场景可摊薄 —— cuDSS 的设计优势用不上。faer 的 AMD+supernodal 已很优。
- **结论**：**Laplace 不用 cuDSS 直接解（会回退）**。GPU 力量应投向迭代法（无 analysis）或逐像素稠密并行核。
  代码保留为证据 + 未来选项。

## V3 —— matrix-free FP64 Jacobi-PCG（网格版，路径 B）

- **背景**：cuDSS 证伪后转向迭代法。无矩阵（matrix-free）PCG 无需符号分析，SpMV 用 5 点 stencil 直接施加。
- **做法**：`laplace_pcg.cu`——Jacobi-PCG，5 点 stencil 无矩阵 SpMV（`M z = deg·z − 邻居和`），deg 场兼作对角
  与内部掩膜；自研块规约点积（部分和拷回主机求和，确定性）；host-in-loop；全 FP64；只需 cudart（无需额外库）。
- **结果**（合成方形网格 profile vs faer，rtol=1e-10）：交叉点 ~250k 未知数；n=1M 时 faer 1307ms vs PCG 460ms =
  **2.84×**；parity max_abs < 6e-7（< 1e-6）。FP64 在 5070 仍够快（PCG 访存受限，非算力受限）。
- **结论**：**路径 B 可行**——大水域用 GPU PCG，小多边形保留 faer。但**此为合成方网结论，待真实地形检验**。

## V4 —— PCG 接入 hydro + 阈值分派 + 真实矩阵验证（commit `778e05d`）

- **背景**：把 PCG 接入 `water-hydro::solve_laplace_dirichlet`，并保证只在数值可靠时用 GPU。
- **做法**：`solve_laplace_dirichlet` 改为分派器（`#[cfg(gpu)]` n_int ≥ 阈值 → GPU，否则/未收敛 → CPU faer
  fallback）；water-gpu 设 optional 依赖 + `gpu` 特性（默认关，纯 CPU 无需 CUDA 也能构建）；rtol 收紧保 parity，
  未收敛回退 faer 保稳定。真实矩阵验证：5 个 Python 生成的不规则域夹具 + 大圆盘 vs faer。
- **结果**：夹具 vs Python 期望 max_abs 4.6e-9、圆盘 vs faer < 1e-6；CPU 回归无变化；默认无 gpu 编译 CUDA-free。
- **结论**：GPU 路径安全接入（阈值 + fallback + parity 门），可在真实数据上验证收益。

## V5 —— 真实地形三方对比规范（commit `3ee6bd9`）

- **背景**：合成基准过于乐观，需强制在真实地形上做 Python / Rust / GPU 三方对比。
- **做法**：确立规范并写入 AGENTS.md——每个 GPU 加速点必须在真实地形（linzhi_clip / 全量林芝）导出的
  **同一真实计算系统**上三方端到端计时并记录到 docs/CUDA.md。工具：`WATER_LAPLACE_DUMP_DIR` 转储真实系统
  `.bin` + bench 例子（faer+GPU）+ Python spsolve 脚本。
- **结果**（clip 大河 n=75,356，e2e best-of-3）：Python spsolve 207ms、Rust faer **43ms**（最快）、GPU PCG 230ms（最慢！）。
- **结论**：**真实地形颠覆合成结论**——clip 最大水体仅 7.5 万 << 交叉点，且真实河道细长、CG 收敛慢，真实交叉点
  远高于合成 25 万。GPU 收益需全量林芝（百万级）大江大河。**「真实地形三方对比」成为此后每次优化的硬性验收项。**

## V6 —— 紧凑变量 PCG：修复真实细长河灾难性回退（commit `3722002`）

- **背景**：拿到全量林芝（1.9GB DEM）真实数据，最大 Laplace 系统 **n=413,968（2686×5771，bbox 填充率仅 2.7%**
  ——真实河道细长稀疏）。
- **做法**：诊断发现初版**全网格** matrix-free PCG 在整个空 bbox 上跑 stencil，做约 37× 无用功。改为**紧凑变量 PCG**
  （`k_spmv_compact` + `water_laplace_pcg_compact`）：只对 n 个真实变量存邻居下标数组、stencil 只遍历变量，不碰空 bbox。
- **结果**：GPU 从**比 faer 慢 12 倍（4708ms）** → **431ms（11× 提速）**。但 GPU kernel 368ms / **1203 迭代**
  （细长河 Jacobi-PCG 收敛慢，同规模紧凑方网仅 ~640 迭代），故 e2e 仍**略慢于 faer 399ms**。
- **结论（诚实）**：紧凑 PCG 把 GPU 从「12× 回退」救回到「与 faer 持平（略慢）」；**Jacobi 预条件不足以在真实
  林芝大河反超**。阈值临时设 500k（保护性，让真实数据全走 faer 零回退）。**决定性反超需 multigrid 预条件**（列为下一迭代）。
  合成方网 2.84× 是乐观上界，真实细长河达不到。

## V7 —— 聚合多重网格（MG）预条件：真实大河决定性反超 faer（commit `5baae61`）

- **背景**：V6 定位瓶颈——细长河低频误差需**粗网格校正**，Jacobi 预条件对此无能为力（迭代数随规模爆炸）。
- **做法**：实现 **unsmoothed aggregation 多重网格 V-cycle 预条件**（`laplace_mg.cu` + `mg.rs`）。2×2 网格聚合逐层
  粗化，Galerkin 粗算子 `A_c = P^T A_f P`（P = 分片常数注入延拓，R = P^T）；因 2×2 方形聚合下粗图仍 ≤4 度网格，
  **各层保持加权紧凑 5 点算子**，复用 GPU SpMV/Jacobi。对称 V-cycle（前/后各 2 次阻尼 Jacobi ω=0.8 + 最粗层 40 次）
  → 预条件 SPD → CG 有效、保真。聚合天然贴合拓扑，对细长河比节点几何粗化稳健。层次主机构建、展平上传，GPU 跑 V-cycle。
- **结果**：迭代数降到**网格无关**的 ~30-60（不再随规模爆炸）。
  - 真实林芝大河 n=414k：**1203 迭代 → 60 迭代**，GPU kernel **370ms → 74ms（5×）**，端到端 **~140ms vs faer 406ms = 2.9×** ⚡。
  - 合成方网：n=4k→1M 时 MG 迭代恒 22-42（Jacobi 132→1415）；n=1M MG kernel 86ms vs faer 1332ms = **15.5×**。
  - parity：合成 vs faer 3e-11~3e-7、真实夹具 2e-11、578k 圆盘 8.6e-9，全 < 1e-6。阈值下调至 150k。
- **结论**：紧凑变量（免空 bbox）+ MG 预条件（降迭代）**双管齐下，GPU 在真实林芝大河端到端 2.9× 反超 faer**
  ——GPU Laplace 的真正价值兑现。

## V8 —— 主机并行化：瓶颈从 GPU 转移到主机后再加速（commit `0f81c67`）

- **背景**：MG 落地后精确分解真实大河（n=414k，e2e ~260ms）：GPU kernel 仅 ~82ms，而主机**单线程**装配
  （`build_pcg_compact` ~64ms）+ 层次构建（~56ms）合计 ~120ms 成了**新瓶颈**。
- **做法**：① `build_pcg_compact` 用 rayon 逐行并行扫描收集变量列 → 前缀和全局编号 → 逐变量并行装配 diag/nbr/b；
  索引反查表改 i32（省一半内存）。② MG 层次构建去 HashMap：2×2 聚合改稠密块表（粗 bbox = 细/4）代替
  `HashMap<(i32,i32)>`；Galerkin 边权直接累加到粗邻居槽（粗图 ≤4 度，免全局边表）。数值与原实现一致。
- **结果**：装配 64ms → 35ms；真实大河 **e2e 260ms → 200ms（2.1× vs faer 419ms）**。parity 全保持。
- **结论**：瓶颈随优化会转移——MG 后 GPU 不再是瓶颈，主机单线程工作才是。并行化后 GPU kernel（~90ms）与主机
  重新成为共同焦点，指向下一步的 GPU 侧优化（混合精度）。

## V9 —— 混合精度 FP32 V-cycle 预条件

- **背景**：V8 后 GPU kernel（~82ms/60 迭代）与主机重新共为焦点。RTX 5070 的 FP32 吞吐是 FP64 的 64×，
  且 MG 访存受限——预条件**只需近似**（外层 CG 保 FP64 → 最终精度/parity 不受影响，只影响迭代数），
  故可把 V-cycle 降到 FP32、显存流量减半。
- **做法**：把 V-cycle 的 stencil 核（SpMV/Jacobi/残差/限制/延拓）模板化于精度 T，实例化为 **float**；
  层次算子 diag/wgt 存 FP32、工作缓冲 FP32；**外层共轭梯度保 FP64**（A_0 单位权 SpMV 用第 0 层 FP64 对角，
  残差递推/点积皆 FP64）；每次预条件应用以 `k_d2f`（残差 FP64→FP32）→ FP32 V-cycle →`k_f2d`（FP32→FP64）桥接。
- **结果**（真实大河 n=414k）：迭代数**仍为 60**（FP32 预条件未损收敛）；GPU kernel **82ms → 72ms（~13%）**，
  H2D 因 FP32 层次减半，e2e **200ms → 187ms（2.14× vs faer 400ms）**。parity 全保持（夹具 2.0e-11、
  578k 圆盘 vs faer 8.5e-9 < 1e-6，n=4096 合成 3.3e-11）。
- **结论（关键发现）**：混合精度收益**低于预期**（预期 ~1.7×，实测 ~1.13×）——说明 **GPU kernel 是「启动受限」
  （launch-bound）而非「带宽受限」**：V-cycle 每层 pre/post 光滑 + 最粗层 40 次 Jacobi + 外层每迭代 3 次
  点积的 D2H 同步，整个求解 ~6000+ 次微核启动 + 180 次 D2H。FP32 只减带宽、不减启动开销。**下一步应主攻
  减少核启动/同步**（V11），而非继续压带宽。混合精度仍为正收益且 parity 零风险，保留。

## V10 —— 减少设备分配（评估后降级）

- **背景**：曾观测 H2D 段（含逐层 cudaMalloc）耗时波动大（9–93ms），疑为分配开销。
- **评估**：V9 FP32 层次已把上传量减半；warm 分配器下 H2D 稳定在 ~7ms。合并 slab + pinned 内存的
  收益（削几 ms）已很小，且引入分配管理复杂度。
- **结论**：**降级/暂缓**——当前 H2D 非瓶颈（~7ms）。若未来批量小系统频繁重分配再考虑内存池复用。

## V11 —— CUDA 图重放 V-cycle：消除 launch-bound 开销

- **背景**：V9 发现 kernel 是 launch-bound——每次 PCG 迭代的 V-cycle 有 ~96 次微核启动（各层 pre/post 光滑、
  最粗层 40 次 Jacobi、残差/限制/延拓），整个求解 ~6000+ 次启动，启动开销占了 kernel 时间的大头。
- **做法**：**V-cycle 是固定核序列、无数据依赖分支**（层数/尺寸/指针每次相同，只有输入 `lv[0].b` 内容变），
  故可用 **CUDA 图**捕获一次、每迭代**重放一次图**（~96 次启动 → 1 次图启动）。把 V-cycle 全部核改为异步于
  非默认 stream（`cudaMemsetAsync`/`cudaMemcpyAsync` + `<<<...,stream>>>`），`cudaStreamBeginCapture` 捕获
  → `cudaGraphInstantiate` → 循环内 `cudaGraphLaunch`。外层 CG 各核与点积也移到同一 stream（点积异步拷回 + 流同步）。
- **结果**（真实大河 n=414k）：GPU kernel **72ms → 28.6ms（2.5×！）**，e2e **187ms → 154ms（2.7× vs faer 413ms）**。
  迭代仍 60，parity 全保持（夹具 2.0e-11、578k 圆盘 vs faer 8.5e-9 < 1e-6）。
- **结论**：**印证 V9 的 launch-bound 判断**——图重放直接把 kernel 砍到 1/2.5。GPU kernel（28.6ms）已很小，
  瓶颈**再次回到主机**（装配 32ms + 层次构建 45ms + 结果写回 ~40ms，合 ~117ms，占 e2e 大头）。指向下一轮主机并行化。

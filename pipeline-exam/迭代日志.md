# 外部（CPU 流水线）优化迭代日志（Water2GPU · hydro 主机侧）

> 本文档记录 Water2GPU 中**非 GPU** 部分——即 hydro 整条 CPU 流水线（`water2rust hydro`：
> IO / warp / 栅格化 / 瓦片 / 逐河流多边形几何+求解 / 裙边等）**每一次优化迭代的决策与结论**。
> GPU 计算核（Laplace 求解器）的迭代记录在 [cuda-exam/迭代日志.md](../cuda-exam/迭代日志.md)，与本文分离。
>
> **方法**：先插桩测量（env `WATER_HYDRO_PROFILE=1`）再动手，拒绝凭假设优化；每步 **md5 逐位校验**输出不变。

---

## H1 —— 全流水线 profile：证伪「IO/栅格化/瓦片占大头」

- **背景**：全量林芝 hydro **47s**（输出 18138×26492 ≈4.8 亿像素）。直觉以为 IO / 栅格化 / 瓦片是大头。
- **做法**：给瓦片路径（`pipeline.rs`）+ `compute_water_surface` + `solve_river_polygon_surface` 三层加 env-gated 分步计时。
- **结果（纠正假设）**：全 47s 中——全幅铺底读 4.75–9.4s（IO，OS 缓存波动）、瓦片墙钟 32.9s、输出写盘 1.3s。
  瓦片内（跨 4 线程累加）：读 6.9s、warp 15.7s、**解算 75.9s**、组合 1.6s。解算再拆：**逐河流多边形 river_solve 50.3s**
  （66%，集中在 414k 主河瓦片 24.5s）、**抬升+裙边 24.7s**（均匀 ~4s/瓦片，与水量无关）、**栅格化仅 0.25s（可忽略！）**。
- **结论**：**栅格化根本不是瓶颈**。真瓶颈是 river_solve（逐多边形河流几何+求解）与 skirt/floor（全网格逐像素），
  其次 warp、IO。且 CLI 未接 GPU、Laplace 走 CPU faer（但线性解本身仅 ~0.5s，非瓶颈）。

## H2 —— 定位到 `spatial_p30_clamp`：全网格秩滤波只用稀疏站点

- **背景**：H1 发现 river_solve 是大头。再给其 11 个子阶段插桩（阈值 >1s 才打印）。
- **结果**：414k 主河多边形（12055 站点）21.76s 中——**`spatial_p30_clamp` = 17.63s（81%！）**，gauss_clamp 2.36s，
  medial/edt ~1s，**Laplace 线性解仅 0.50s**。
- **根因**：`spatial_p30_clamp` 对 z_smooth 做「空间 P30 下压」，其 `percentile_filter_2d` 在**整个 lh×lw 网格
  （15.5M 像素）**跑 O(h·w·size²) 的秩滤波，**但结果只在 ~12k 个骨架站点像素被读取**——其余 99.9% 像素纯属无用功
  （与 GPU 侧「紧凑变量免空 bbox」如出一辙）。
- **修复**：water-core 新增 `percentile_filter_2d_at(data, pct, size, points)`——只在给定查询点算秩滤波，与全网格版
  **逐位一致**（同 reflect 边界 / 窗口填充顺序 / NI_Select）；`spatial_p30_clamp` 改为只在站点算。
- **结果**：主河 p30 **17.63s → 0.06s（294×）**，river_solve 21.76→4.37s。**全 hydro 47s → 33s**（1.43×），
  输出 **md5 逐位一致**（golden 校验通过）+ river 核对拍 + 新原语单测通过。
- 附带 H2b：`solve_laplace_per_polygon` 逐多边形循环并行化（rayon + 串行序缝合 = 逐位一致）——但大河是单巨多边形
  主导，收益小（~2.5s）；仍保留（多多边形瓦片受益）。
- **结论**：又一次「全域算、稀疏用」的浪费——只在真正需要的点计算即得两个数量级提速，且零精度损失。剩余热点：
  gauss_clamp（~9s，全网格高斯只用站点，但可分离难限点、有 parity 风险，暂缓）、warp/IO（eci-gdal 子模块）、
  skirt EDT+膨胀（~4s/瓦片，全网格，可 bbox/并行，待办）。

> 工具：`WATER_HYDRO_PROFILE=1` 打印 pipeline / compute_water_surface / river_solve 三层分步耗时。

## H3 —— 提高瓦片并行度：用起闲置核（4→6 线程）

- **背景**：p30 修复后重新 profile（全 hydro ~33s）。真热点（跨线程累加）：**抬升+裙边 24.8s**、warp 15.6s、
  river_solve 内 **gauss_clamp 8.6s**、IO 读写 ~17s、medial/edt ~3.5s、faer laplace 1.1s。关键观察：
  瓦片池仅 **4 线程**（历史为控内存），机器却有 **24 核**——**20 核闲置**。
- **做法**：瓦片线程数 4→6（含水瓦片一般 ≤6，全并发），加 env `WATER_HYDRO_TILE_WORKERS` 可调；
  峰值内存 ~并发瓦片数 ×~3GB。
- **结果**：瓦片处理墙钟 **23.4s → 15.1s（1.55×）**，全 hydro **33s → 29s**，峰值 RSS 14.2→18.8GB（31GB 机安全），
  输出 **md5 逐位一致**。
- **结论**：CPU「慢」很大程度是**并行度不足**而非算力不足。瓦片级到 6 核后，串行的**全幅铺底读（9.4s）**升为
  次大项（且 DEM 被读约 2×：全幅铺底 + 各瓦片窗口，可去重）；瓦片内仍单线程，**内层并行（用满 24 核）是下一步**。

## 分析 —— 「CPU 表现差的部分搬到 GPU 会不会更快？」

> 用户问题。基于上面实测热点，逐项给出**证据化判断**（GPU 收益 = 数据并行度 × 访存/算力受限 ×
> 单次数据量能否摊薄 H2D/D2H；PCIe ~12GB/s，70M px×4B≈280MB 往返 ~50–90ms）。

| 热点 | 累加耗时 | 性质 | CPU 侧解法 | 搬 GPU 判断 |
| --- | --- | --- | --- | --- |
| skirt EDT+膨胀+floor | 24.8s | 全网格 EDT/形态学，数据并行、**访存受限** | 并行（用满核）/ 限 bbox | **GPU 有利**（5–10×），单瓦片 70M px 够大能摊薄传输——但**先用 CPU 并行** |
| warp 重投影 | 15.6s | 重采样，数据并行、访存受限 | eci-gdal 子模块 | GPU 可（GDAL GPU warp），但**子模块大改**，性价比中 |
| gauss_clamp（river） | 8.6s | 可分离高斯，数据并行 | 并行 / 稀疏 scatter | GPU 有利，但**小多边形传输开销吞掉收益**（只大多边形值得） |
| IO 读+写 | ~17s | 磁盘 + 解码，**IO 受限** | 去重（DEM 读 2×）、并行解码 | **GPU 无用**（磁盘 IO 不吃 GPU）；解码走 nvCOMP 是大改 |
| medial_axis | 1.8s | 迭代细化，**顺序依赖**（tiebreaker） | 难 | **GPU 不利**（本质顺序，映射差） |
| edt（river） | 1.7s | 可分离 EDT | 并行 | GPU 可但**量小**、每多边形传输不划算 |
| faer laplace | 1.1s | 稀疏 Cholesky | 已有 GPU MG-PCG（阈值 150k） | 已评估：现总量太小，不值得 |

**结论（回答用户）**：
1. **CPU 慢的主因是「没用满核」而非「算力不够」**——20/24 核曾闲置。**优先把 CPU 并行做透**（瓦片级已到 6 核；
   再做**内层并行**：skirt 的 EDT/膨胀、gauss、per-polygon 用 rayon 铺满 24 核）。这一步**零传输、零 parity 风险、
   零 CUDA 复杂度**，预计把 skirt 24.8s、gauss 8.6s 再砍数倍。
2. **搬 GPU 真正值得的只有**：单瓦片级、稠密、数据并行、访存受限的 **skirt EDT+形态学**（70M px 够大摊薄传输，
   5–10×）；warp 次之（但在子模块）。**前提是这些数据量足够大**——per-小多边形的 gauss/edt 搬 GPU 会被
   H2D/D2H 拖死。
3. **搬 GPU 无用/不利**：IO（磁盘受限）、medial_axis（顺序）、已经很小的 faer laplace。
4. **正确顺序**：先榨干 CPU 并行 → 再看残留的稠密瓶颈是否值得上 GPU。别用 GPU 去「暴力算被浪费的工作」
   （p30 的教训：算法/稀疏化 + 并行往往比搬 GPU 更划算）。

## H4 —— 内层并行（并行化 water-core 原语 + 两级瓦片调度）

- **背景**：H3 后瓦片级已到多核，但瓦片**内部仍单线程**；24 核仍未铺满。热点里 skirt 的 EDT/膨胀、river 的
  gauss/edt 都是**可分离/逐像素**，天然可并行。
- **做法**：① water-core 三原语 rayon 并行（**逐位一致**）：`gaussian_smooth`/`_f32`（逐行并行）、`binary_dilation`
  （逐行）、`distance_transform_edt`（列遍/行遍各并行，1D 变换不变）。② 瓦片调度改**两级**：线程池取满核（24），
  按 `mem_tiles`（并发瓦片，限内存）分块 `par_iter`，块内瓦片 + 其内层并行借空闲线程铺满 CPU。
- **结果**：river_solve 解算（跨线程累加）**44s → 26s**（内层并行确实压缩了计算）；但**全 hydro 墙钟没降**
  （~28–29s，与 H3 持平）。内存对并发瓦片数敏感：mem_tiles=6 时 RSS 31.6GB **爆内存→换页→反而 51s**；
  取 **3（~19GB）** 安全且墙钟 ~29s。输出 **md5 逐位一致**，river/water-core 对拍全过。
- **关键结论**：**计算已不再是瓶颈**——内层并行把 river/skirt 压下去后，全 hydro 墙钟被**新的地板**卡住：
  **warp 重投影 15.6s（eci-gdal 子模块，串行/瓦片）+ 全幅铺底读 9.3s（IO 解码）**。要再降 hydro 墙钟，
  必须动 **warp**（子模块，或**搬 GPU**——这是唯一真正值得上 GPU 的稠密访存受限点）与 **IO**（DEM 被读 ~2×，
  可去重；磁盘解码 GPU 无用）。**这正印证了前面的 GPU 取舍分析**：CPU 并行榨干后，warp 成为唯一的 GPU 候选。
- 附：`WATER_HYDRO_TILE_WORKERS` 可调并发瓦片数（小内存机降、大内存机升）；线程池恒取满核。
